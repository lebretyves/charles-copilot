01 — Recadrage produit

Ce que VAIA est — et ne sera pas au départ

Le cadre réglementaire européen (MDCG 2019-11 / 2025) regarde la finalité revendiquée pour qualifier et classifier le logiciel. Un MVP trop ambitieux dans sa communication = classification IIb/III immédiate. Le bon positionnement dès le départ change tout.

VAIA EST
Un copilote de vigilance peropératoire non prescriptif, explicable, focalisé sur 1 à 2 événements au départ. Il détecte, agrège, alerte. Le clinicien décide toujours.
VAIA N'EST PAS
Une IA qui fait l'anesthésie. Un outil qui prescrit. Une plateforme pré-per-post-op complète dès le départ. Une promesse de décision thérapeutique autonome.

06 — Feuille de route technique

Du simulateur au connecteur réel

Ton hardware est parfait — AMD Ryzen AI 7 350, 32 Go RAM, NPU intégré. Aucun achat nécessaire pour les 3 premières étapes.

Étape 1 — Simulateur (cette semaine) — 0€

Ce que le simulateur doit produire

  • 5 scénarios : hypotension, bronchospasme, saignement occulte, curarisation résiduelle, normal
  • 3 phases par scénario : pre_event · event · post_event
  • Champ vaia_detectable: bool — ce que VAIA voit avant le moniteur
  • Champ monitor_would_alarm: bool — ce que le moniteur classique voit
  • Paramètres perop complets : hr, sbp, dbp, map, spo2, etco2, peak_pressure, compliance, peep, bis, temp
  • Publication MQTT bloc/{patient_id}/vitals toutes les 5 secondes
Le delta entre monitor_would_alarm=False et vaia_detectable=True est la valeur clinique de VAIA. C'est ce que tu montres à Botrel mercredi et Gayat vendredi.

HL7 vs FHIR — Quand utiliser quoi : HL7 v2.5 pour la connexion aux moniteurs en temps réel (protocole legacy mais dominant dans tous les blocs). FHIR R4 pour récupérer le dossier patient (ASA, antécédents). Les deux sont pour l'étape 3 seulement — pas maintenant.

Architecture logicielle propre — Ordre de priorité

  • Validation Pydantic stricte à l'entrée — bornes physiologiques, try/except, logging si métrique manquante
  • Journal d'événements complet — chaque alerte tracée avec timestamp, version modèle, paramètres déclencheurs
  • Versioning modèle avec MLflow — obligatoire avant tout déploiement clinique (IEC 62304)
  • Tests unitaires pytest — 20 tests minimum sur AlertEngine et AlertState
  • Séparation stricte : simulateur / moteur alertes / interface / LLM (surcouche uniquement)
  • CHANGELOG.md versionné — dès v0.1.0, document le plus demandé par les organismes notifiés
  • SOUP.md — liste toutes les dépendances tierces (exigence IEC 62304)

10 — Zones de danger

Ce qu'il ne faut pas faire

Données CHU avant cadre formalisé
Même si le MAR est d'accord verbalement. Même si tu travailles dans le service. La CNIL et la responsabilité pénale sont réelles. Convention + DPO + protocole avant tout.
Promettre une classe réglementaire fixe trop tôt
La classification MDR dépend de la finalité revendiquée. Si tu dis "aide à la décision thérapeutique" tu passes en IIb. Rester sur "aide à la vigilance non prescriptive" jusqu'à la validation juridique formelle.
Donner des parts trop tôt
Pas de parts "à la parole". NDA → convention → vesting conditionné → parts. Toujours.
Confondre démo et produit certifiable
Ce que Codex génère en 2 jours est une démo. Jamais du code de production médicale. Le CTO senior fait la différence entre les deux.
S'engager verbalement sur Epitech sans écrit
L'accord oral du responsable pédagogique ne vaut rien si les règles changent. Tout obtenir par email.
Laisser croire que le CHU est copropriétaire par défaut
Les algorithmes et le code restent dans ta SAS. Le CHU est partenaire de recherche, pas co-propriétaire. Le préciser dans la convention dès le départ.
